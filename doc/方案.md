针对你在安卓开发中遇到的微信 `content://` URI 文件名混淆（Hash化）的问题，这通常是因为微信在处理“直接转发”或“本地分享”的文件时，为了安全和避免路径冲突，通过其 `FileProvider` 对外暴露的是经过处理的虚拟路径。

要获取文件的真实名称，可以尝试以下几种方案：

### **方案一：使用** **`ContentResolver`** **查询（推荐）**

即使 URI 路径中显示的是乱码或 Hash 值，标准的 Android `FileProvider` 通常会在其数据库中存储文件的元数据。你可以通过 `ContentResolver` 查询 `OpenableColumns.DISPLAY_NAME` 字段，这通常能返回原始文件名。

**实现代码参考：**

**Java**

```
public String getFileNameFromUri(Context context, Uri uri) {
    String fileName = null;
    if (uri.getScheme().equals("content")) {
        try (Cursor cursor = context.getContentResolver().query(uri, null, null, null, null)) {
            if (cursor != null && cursor.moveToFirst()) {
                // 尝试获取 DISPLAY_NAME 字段
                int nameIndex = cursor.getColumnIndex(OpenableColumns.DISPLAY_NAME);
                if (nameIndex != -1) {
                    fileName = cursor.getString(nameIndex);
                }
            }
        } catch (Exception e) {
            e.printStackTrace();
        }
    }
    
    // 如果查询不到，或者不是 content 协议，回退到从路径截取
    if (fileName == null) {
        fileName = uri.getPath();
        int cut = fileName.lastIndexOf('/');
        if (cut != -1) {
            fileName = fileName.substring(cut + 1);
        }
    }
    return fileName;
}

```

***

### **方案二：扩展文件尾部的自定义元数据**

既然你的插件已经具备了读写文件尾部（Metadata）的能力，这是最可靠的“内生”方案。微信可能会修改文件名或路径，但它通常不会改动文件的二进制内容。

**优化方案：** 在写入密码和 UID 到文件尾部时，顺便**将原始文件名也写入尾部**。

- **写入结构示例：** `[原始文件内容] + [文件名长度(int)] + [文件名] + [UID] + [Password]`
- **读取逻辑：** 插件启动后，先不管 URI 叫什么，直接读取文件流的末尾，解析出原始文件名。
- **优点：** 彻底解决文件名丢失问题，且即便用户在微信里手动重命名了文件，你的插件依然能找回最初的业务名称。

***

### **方案三：从** **`Intent`** **的其他字段尝试获取**

有时微信在发送 `Intent` 时，会在 `extras` 中携带一些辅助信息。虽然不如 `ContentResolver` 稳定，但可以作为辅助：

1. 检查 `Intent.EXTRA_SUBJECT` 是否包含文件名。
2. 在某些低版本或特定场景下，微信可能会传递 `file_name` 这种非标准 Key。

**Java**

```
// 调试时打印所有 extras
Bundle extras = getIntent().getExtras();
if (extras != null) {
    for (String key : extras.keySet()) {
        Log.d("ProxyActivity", "Extra key: " + key + " value: " + extras.get(key));
    }
}

```

### **方案四：临时文件策略（针对场景二的妥协方案）**

如果在场景二中 `ContentResolver` 依然返回 Hash 后的名称（微信某些版本确实会强行隐藏），你可以采取以下逻辑：

1. **检测 Hash 文件名：** 判断文件名是否符合混淆特征（如长度为 32 位的 MD5 字符串）。
2. **内容识别：** 既然文件尾部有 UID，你可以根据 UID 去你本地的 `/Documents/wpspasswordmanagement` 目录或数据库中匹配。
3. **重命名副本：** \* 读取文件流，通过文件尾部的 UID 找到历史记录中的原始文件名。
   - 在拷贝副本到指定目录时，**手动将其重命名**为匹配到的原始名称。

### **总结建议**

1. **首选方案一：** 使用 `OpenableColumns.DISPLAY_NAME` 这种标准做法，能解决 90% 的 `ContentProvider` 文件名获取问题。
2. **增强方案二：** 在文件尾部额外记录一份文件名，作为你插件生态内的“真理来源”。

考虑到你目前已经在做 WPS 办公自动化和 LDAP 集成，建议采用**方案一 + 方案二**的组合方式，既符合 Android 规范，又能通过业务数据闭环解决特殊场景下的文件名丢失。
